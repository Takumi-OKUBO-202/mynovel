# 単話添削(厳しい読者目線での改稿)

第8〜11話のフィードバック改稿で確立した工程。**1話を、初見の読者の目で一文ずつ読み直し、`CLAUDE.md`の規約に照らして直しきる。** エージェントは使わず、本人(このセッションのClaude)が直接編集する。

**規約の本体は`CLAUDE.md`「文体規約」以下の全節。** このスキルは手順と道具だけを持つ。規約をここに複製しない(二重管理になる)。

## 手順

### 1. 前提を読み込む(本文を直し始める前に必ず)

- 対象話の本文と**冒頭メタコメント**(過去の改稿理由。同じ轍を踏まないため)
- **直前2話**——締めの型・場面構成・情報の渡され方が3話連続していないかは、並べないと判定できない
- **後続話への鎖**——対象話が触れる持ち物・状態・開示順が後の話の前提になっていないか。`bible/characters/*.md`の登場記録と`bible/timeline.md`で当たりをつけ、疑わしい話は本文を開く(例: 傷薬の本数は第11〜19話で鎖になっている。回復の開示は第12話の口頭→第13話の実演の順)
- `plot/arcs/`の該当行(その回の狙い。**冒頭の動機と山場が一致しているか**の照合元)
- `plot/foreshadowing.md`(仕込み・回収の予定に触れる編集をしていないか)
- 本文が触れるシステム・地理・人物の`bible/`該当箇所(スキル名表記・習性・方角)

### 2. 機械チェックを流す

```bash
python3 .claude/skills/tensaku/scripts/lint.py manuscript/partNN/epNNN.md
```

文字数 / た。段落4連続 / 4文段落 / 数字混入 / 反復語 / 空行・◇書式 が出る。**結果は材料であって結論ではない。** ヒットは本文を開いて文脈で判断する。

### 3. 規約に沿って通し読みする

`CLAUDE.md`の節を**チェックリストとして上から順に当てる**。とくに再発が多いのは——

- **読者の手を止めない**(三つの問い。迷ったら消す)
- **読者に伝わるか**: 指示語の指す先(直前1〜2文まで)/主人公が知り得ないこと/現在地の採点/「Aした。今日はAしなかった」対句/仕様前提の否定形/数の明示
- **話を飛ばさない**: 遭遇→戦闘の段差/場所移動の位置関係/判断の見立て/接続語の受け先/消耗の過程/複数戦の一体目の決着
- **戦闘の段取り**(戦闘がある回): 臨戦の描写→必ず一度失敗→失敗から見つけて次で使う→クレストを使う。NPCに解法を言わせない(事実と習性まで)。通知は戦闘後・効果一行付き。**被弾・失敗には構図の理由を付ける**(詠唱中の後衛を庇った等)——理由のない被弾は油断にしか見えない
- **語尾・締め・型**: 締めの型が直前2話と被っていないか/ぼかした締め/意味ありげで情報のない締め/極端な短文
- **キザにしない**: 決めポーズ/脇役の過大な反応/声に出して恥ずかしいか
- **会話**: 単語だけの受けが3つ以上続かないか/その会話でしか出せない情報・感情があるか/**問いかけ・話題が返事のないまま次へ飛んでいないか**(会話は受けて閉じる)/**初見の出来事・新情報に立ち会った人物が無反応になっていないか**(目の前で短剣が槍に変わったのに同行者が触れない、は事故)
- **人物の一貫性**: **確立済みの習慣・経歴と矛盾する反応をさせない**(毎晩攻略サイトを見る主人公が有名な職業名を「初めて聞く」等)。判定は「この人の習慣なら、これを知っているはずでは?」と一度問うこと
- **呼称と境界**: ゲーム内=ウィン/現実=冬夜。ログイン・ログアウトの境界描写
- **数値・金額ゼロ**(擬音・Lv表記・段階は可)

一文ごとに「**この一文で読者に何が渡るか**」を問い、渡らない文は消す。**削って通じるなら要らなかった文。** 足すのではなく置き換える(4,000字目安を動かさない)。

### 4. 直す・記録する

- 本文を直接編集する。**会話の生きた台詞はできるだけ温存**し、直すのは地の文の癖から
- **ただし、違和感の指摘が入った会話は、一行の手直しではなく会話ごと組み直すことを先に検討する。** 元の台詞を残そうとしすぎると、橋渡しの台詞が不自然になり継ぎ接ぎの違和感が出る(第12話の休憩会話で実証済み)。**場面の目的(何を渡す会話か)だけ残して一から書き直すほうが、結果的に早くて自然**
- 直した内容と理由を**対象話のメタコメントに追記**する(「何を・なぜ」を1行ずつ。次の改稿者=未来の自分への引き継ぎ)
- 添削中に**一般化できる欠陥**を見つけたら、`CLAUDE.md`の該当節に規則として追加する(実例と直し方をセットで)。ユーザー指摘から直した項目は必ず一般化する

### 5. 波及を確認する

- 変更した固有名詞・持ち物・状態・開示順で**リポジトリ全体をgrep**し、他話・`bible/`・`plot/`との矛盾を潰す
- 話数レンジ制約(本数の鎖・不在期間・秘密の保持)は、**レンジ内の話を時系列に並べて機械的に照合**する

### 6. 四視点セルフレビュー(必須・第12話フィードバックで新設、第14話フィードバックで四人目を追加)

修正を終えたら、**本文を四回、毎回別の読者になりきって頭から読み直す。** 一周ごとに「見つけた問題を列挙→直す→次の周へ」の順で回す。四周とも指摘ゼロになるまで直してから次へ進む(直したら、その周をもう一度読み直す)。

1. **一周目【小説初心者】——会話の違和感と急展開に厳しい。** 見るもの: その台詞を、その人が本当にその言い方で言うか(声に出して確かめる)/受け答えが噛み合っているか/問いかけが返事のないまま流れていないか/会話から次の場面・話題への飛びがないか/「この人は今なぜこれをしたのか」が読んで分かるか
2. **二周目【VRMMOカテゴリのファン】——ゲーム的違和感と説明不足に厳しい。** 見るもの: 職業・スキル構成に合った行動か(無防備になる選択に理由があるか、被弾に構図があるか)/仕様・UI・システムの整合(詠唱の溜め、通知、画面表示)/ゲーマーなら知っているはずのことを知らない顔をしていないか/ゲーム内マナー(リアル情報を聞く配慮など)/読者が知らない仕様を前提にした描写がないか
3. **三周目【熟練の編集者】——矛盾と登場人物の魅力に厳しい。** 見るもの: `bible/`・前後話・持ち物・開示順との矛盾/その場面で各キャラクターは魅力的に見えているか(得しているか、損な役を押しつけられていないか)/新情報・初見の出来事への反応が書かれているか/冒頭の動機と山場が一致しているか/**後の話に控えている見せ場・会話の縮小版を先にやっていないか**/**台詞の末尾に気の利いた風の付け足しがないか**/この回を読んだ読者が次話を読みたくなるか
4. **四周目【VRMMO人気作品の読者】——ジャンルの快感と萎えに厳しい。** なろう/カクヨムのVRMMO・ゲーム系の人気作を読み込んでいて、「こういうのが読みたくて開いた」がはっきりある読者。二周目(仕様の整合を見る)とは別で、**この周は面白さの市場基準を見る。** 見るもの:
   - **人気のある型が活きているか**: ユニークな固有能力の見せ場(=クレストの「借りて、変える」が今回どこで気持ちよく決まったか)/工夫・搦め手で格上に届く瞬間/新スキル・新要素の「試したくなる」提示/発見・初見コンテンツ(レア職業・レアモンスター・未発見の場所)のワクワク/「この先どうなる?」の引き
   - **萎えの型を踏んでいないか**: 主人公が受け身のまま話が進む(状況に流されてばかり)/もらいすぎ(実力・工夫と釣り合わない報酬・能力・好意)/説明パートが長くて戦闘・探索の足を止める/仲間が空気(いるのに何もしない回)/せっかくのレア要素を淡白に消化する(レアモンスター・レア発見を「ふーん」で流す)/ピンチに緊張感がない(どうせ勝てると読めてしまう)
   - **描写の過不足**: ゲームならではの画面・音・演出(通知・ドロップ・エフェクト)が要所で「見えて」いるか/逆にUI描写が多すぎて日常レポートになっていないか/戦闘の爽快感が言葉で説明されずに絵と音で渡っているか
   - **判定の仕方**: 「この回を人気作の更新と並べて読んだとき、ブラウザバックされない理由を一つ言えるか」。言えないなら、その回の山をどこに立て直すかを考える

**レビューは実際に四回読むこと。** チェックリストを眺めて「たぶん大丈夫」で済ませた周は、やっていないのと同じ。見つけた指摘と直しは、メタコメントに周ごとに記録する。

### 7. 測ってから報告する

- lintを再実行し、**文字数は必ず実測してから**報告・コミットメッセージに書く(過去に4回、実測せず書いて修正になった。**測る前に数字を書かない**)
- **手で数字を書き写さない。** lintと同時にコミットすると、lintの出力を見る前にメッセージを書くことになり必ず事故る。**lintの実行とコミットは別のツール呼び出しに分ける**か、シェル変数で埋め込む(`N=$(python3 -c '…') && git commit -m "…${N}字"`)
- コミットして`claude/…`ブランチと`main`の**両方に**プッシュする
- ユーザーへの報告は日本語で、**直した箇所を「元の文→直した文/理由」の形で列挙**する。分類(蛇足・指示語・段取り…)でまとめると読みやすい

## してはいけないこと

- lintだけ流して「問題なし」と報告する(機械チェックは規約の1割しか見ていない)
- 規約に挙がった型の**新種**を見逃す——規約は実例集であって網羅ではない。判定基準は常に上位ルール「読者の手を止めない」に戻る
- 直した結果の文字数・型が直前2話と揃ってしまう(締めの型・場面構成は3話連続で同型にしない)
- メタコメント・`HANDOFF.md`への記録を省く
